# AIMS 1.0.0 管理员手册

面向现场运维与实施负责人。命令均在目标机上执行，路径按默认安装位置。

- 程序目录：`C:\Program Files\AIMS`
- 数据目录：`C:\ProgramData\AIMS`
- 后端 CLI：`AIMS-Backend\AIMS-Backend.exe deploy <子命令>`

为避免每次都写长路径，下文用：

```powershell
$APP = "C:\Program Files\AIMS"
$BE  = "$APP\AIMS-Backend\AIMS-Backend.exe"
```

## 一、日常运维

### 1.1 启停

| 操作 | 方式 |
|---|---|
| 启动 | 桌面快捷方式（GUI）；开机自启默认最小化到托盘 |
| 停止 | 托盘右键 → 退出（会先停后端，再停数据库） |
| 只停数据库 | `& "$APP\tools\Stop-Aims.ps1" -StopDatabase` |
| 只启动数据库 | `& $BE deploy --root $APP start` |
| 查看状态 | `& "$APP\tools\Get-AimsStatus.ps1"` 或 `& $BE deploy --root $APP status` |

**不要用任务管理器强杀 `postgres.exe`**：会导致数据库进入需要恢复的状态。要停就停整个 AIMS。

### 1.2 健康检查

```powershell
& $BE deploy --root $APP doctor --api-port 8000
& $BE deploy --root $APP status
```

`doctor` 覆盖 14 项：版本一致性、安装文件完整性、数据目录可写、磁盘空间、配置文件、密钥长度、PostgreSQL 版本、集群初始化、服务状态、数据库连通性与扩展、端口、AI 引擎、最近备份。

### 1.3 日志位置

| 日志 | 路径 | 用途 |
|---|---|---|
| 后端运行日志 | `C:\ProgramData\AIMS\Logs\` | 请求异常、调度任务、数据链 |
| 安装报告 | `Logs\install-report.json` | provision 每一步的结果 |
| 安装后自检 | `Logs\post-install-doctor.json` | 安装成功与否的判据 |
| 崩溃日志 | `AIMS\aims_crash.log` | 启动阶段崩溃（含 `sys.path`、`DATABASE_URL`） |
| 备份日志 | `Logs\backup*.log` | 备份/恢复过程 |
| 审计日志（业务） | 界面「系统 → 审计日志」/ `audit_logs` 表 | 登录、用户变更、配置变更 |

日志按大小滚动，默认保留 14 天由 `retention` 任务清理。

### 1.4 运行指标（1.0.0 新增）

`GET /api/v1/system/metrics`（**仅超管**）返回当前进程指标；`?format=prometheus`
输出标准抓取格式，可直接接 Prometheus/Grafana（单机部署也可以只用 `curl` 看）。

```powershell
# 登录拿令牌
$tok = (Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/login `
        -ContentType application/json `
        -Body '{"username":"reladmin","password":"***"}').access_token

# JSON 快照：请求量、状态码分布、p50/p95/p99、并发数、RSS、线程数
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/system/metrics -Headers @{Authorization="Bearer $tok"} |
    ConvertTo-Json -Depth 5

# Prometheus 抓取格式
Invoke-WebRequest -Uri 'http://127.0.0.1:8000/api/v1/system/metrics?format=prometheus' `
    -Headers @{Authorization="Bearer $tok"} | Select-Object -ExpandProperty Content
```

指标特征：

- **重启清零**：进程内计数，重启后归零——"重启就恢复正常"本身是一条有用信号
- **路由标签归一化**：`/devices/12` 记为 `/devices/{id}`，不会因为 ID 多而爆标签
- **慢请求**：≥3 秒的请求在日志里记 WARNING（带 `request_id`），5xx 记 ERROR
- **结构化日志**：设置环境变量 `AIMS_LOG_FORMAT=json`（`Config\aims.env`）后，
  日志每条一行 JSON，可直接被采集器消费；不改则保持文本格式

## 二、备份与恢复

### 2.1 自动备份

- 安装完成时自动做首份备份
- 每次升级前自动备份（`--reason pre-upgrade`）
- 每次恢复前自动备份当前数据（`pre-restore-*`）
- 计划任务 `AIMS Backup` 每日执行（安装时若勾选）

备份产物：`C:\ProgramData\AIMS\Backup\aims-<时间戳>.dump` + 同名 `.meta.json`（版本、时间、大小、SHA-256、耗时）。

### 2.2 手工备份

```powershell
& "$APP\tools\backup.ps1"                                   # 备份到数据目录
& "$APP\tools\backup.ps1" -Reason pre-maintenance -Export E:\aims-backup   # 同时复制到 U 盘/网络盘
& "$APP\tools\backup.ps1" -Keep 20                          # 保留最近 20 份
```

或开始菜单「AIMS 备份与恢复」（**全程无黑窗**，完成后弹窗告知成功/失败与文件路径）。

### 2.3 恢复

**恢复会覆盖当前数据库**，要求 AIMS 已关闭：

```powershell
& "$APP\tools\Stop-Aims.ps1" -Quiet -StopDatabase
& $BE deploy --root $APP backups                 # 列出可用备份
& $BE deploy --root $APP restore latest --yes    # 或 restore <文件名> --yes
```

恢复后自动做一次"恢复前数据"备份（`pre-restore-*`），误操作可再恢复回来。

### 2.4 验证备份可用（建议每月一次）

1. 备份 → 2. 在测试机恢复 → 3. 跑 `deploy doctor` 与界面自检 34 项 → 4. 抽查设备/报警/知识库是否为最新。

**只备份不验证 = 没有备份。** 备份文件是同版本 PostgreSQL 的 `pg_dump -Fc` 归档，跨大版本恢复需先升级数据库。

## 三、升级与回滚

### 3.1 升级前检查清单

- [ ] 当前版本 `& $BE deploy --root $APP version`
- [ ] 磁盘剩余 ≥ 10 GB（升级要留旧程序副本）
- [ ] 已有一份当天备份
- [ ] 记下当前 `Logs\post-install-doctor.json` 的结论作为对照

### 3.2 升级

用新安装包覆盖安装（推荐），或：

```powershell
& "$APP\tools\upgrade.ps1"
```

流程：备份 → 停程序（数据库保留，迁移需要）→ `deploy upgrade`（只增表/增列/装扩展）→ `deploy doctor` → 失败则还原 `rollback\<旧版本>` 并用升级前备份恢复数据库。

### 3.3 回滚

```powershell
# 程序文件回滚
robocopy "$APP\rollback\0.9.9\AIMS-Backend" "$APP\AIMS-Backend" /MIR

# 数据库回滚
& $BE deploy --root $APP restore <升级前备份文件名> --yes
```

**先回滚程序再回滚数据库**：新版本可能已写入新列，旧程序读新库通常兼容，但反过来不一定。

### 3.4 降级保护

用旧安装包覆盖新版本时，安装程序会比对版本号并警告（需要用户显式确认）。生产环境请拒绝，改用新版安装包或按 3.3 回滚。

## 四、用户与权限

| 角色 | 能力 |
|---|---|
| 普通用户 | 业务数据读写、模板使用与自建、知识库使用、AI 问答/诊断 |
| 管理员（`is_superuser`） | 以上全部 + 用户管理、审计日志、系统设置写入、外部数据源、AI 模型加载/卸载/删除/扫描、组件信息 |

关键边界（1.0.0 已加固）：

- 用户清单、审计日志、用户创建 —— **仅管理员**
- 模型扫描/加载/卸载/删除 —— **仅管理员**，删除还需 `?confirm=true`，激活中的模型拒绝删除
- 模板：编辑/删除/回退仅**创建者或管理员**；系统内置模板改名/改分类/删除对所有人 403
- 报警确认人由服务端取认证身份，客户端传入会被忽略（防伪造）

用户管理命令：

```powershell
& $BE deploy create-admin            # 新建管理员（无默认口令）
& $BE deploy reset-password          # 重置口令
& $BE deploy list                    # 列出用户
```

口令策略：最小长度、复杂度、常见口令拒绝、连续失败锁定（用户名 5 次/15 分钟、IP 20 次/15 分钟）。

## 五、AI 引擎与模型

### 5.1 引擎状态

界面「AI 中心 → 引擎信息卡」显示：引擎后端、模型目录、可用模型数、当前激活模型。
命令行：

```powershell
& $BE deploy --root $APP ai-probe     # 含模型加载自检
```

没有 llama.cpp 或没有模型时，AI 自动降级为**规则引擎**：问答与诊断仍可用，只是不做本地大模型推理。`doctor` 会如实报告"本地推理不可用：ModuleNotFoundError: No module named 'llama_cpp'"，这不是故障。

### 5.2 导入本地模型

1. 把 `.gguf` 文件放到 `C:\ProgramData\AIMS\Models\`
2. 界面「AI 中心 → 模型 → 扫描本地模型」（或 `POST /api/v1/ai/cores/scan-local`）
3. 系统校验 GGUF 魔数、计算 SHA-256、登记来源为 `local-import`（重复扫描不会重复登记）
4. 在模型列表点"加载"设为激活模型

### 5.3 卸载 vs 删除

| 操作 | 效果 | 权限 |
|---|---|---|
| **卸载** | 仅从内存/显存释放，文件仍在磁盘，下次可秒级重新加载 | 管理员 |
| **删除** | 删除注册记录（可选删除文件），**必须** `?confirm=true`；激活中的模型、规则包、模型目录之外的路径一律拒绝 | 管理员 |

**卸载不删数据、删除要确认**——这是为了让"腾内存"和"清磁盘"两件事不混淆。

## 六、数据保留与容量

`retention` 任务每天 03:30 执行，启动时也会扫一次孤儿导入批次。清理规则（可在「系统 → 设置」调整天数）：

| 数据 | 默认保留 | 说明 |
|---|---|---|
| `measurements` 测点数据 | 按 `data_retention_days`（默认 365 天） | 分块删除，避免长事务锁表 |
| `acquisition_events` 采集事件 | 同上 | 按天切片 |
| `audit_logs` 审计日志 | 按配置（默认 180 天） | 合规要求长的请调大 |
| `sync_logs` 同步日志 | 默认 90 天 | |
| `snapshots` 快照 | 默认 90 天 | |
| `login_failures` 登录失败 | 15 分钟窗口外即可清 | 用于锁定判定 |

容量估算（单设备 100 测点、5 分钟采样）：约 **1050 万条/年**，压缩后约 1.2–1.8 GB/年。建议按现场规模设置保留天数与磁盘告警阈值。

磁盘不足时 `doctor` 会报 `磁盘空间` 项，低于 2 GB 时前端也会提示。

## 七、性能基线（可对比）

在 Linux + PostgreSQL 16.15 + 39 万条测点数据的环境实测（`tools/perf_bench.py`）：

| 项 | 结果 |
|---|---|
| `/health` | p50 0.6 ms / p95 1.2 ms |
| 看板统计 | p50 1.5 ms / p95 2.5 ms |
| 设备列表（50 条） | p50 2.7 ms / p95 3.1 ms |
| 模板中心列表 | p50 4.9 ms / p95 5.2 ms |
| 报警列表（50 条） | p50 1.5 ms / p95 2.2 ms |
| 并发吞吐（8 线程） | 约 279 QPS，错误 0 |
| 导入（宽表 2 万行 → 6 万条读数） | 4.5 s，约 13251 条/秒 |
| 稳定性（90 s 持续压测） | 865 请求 0 错误，RSS 持平，线程数不增长 |
| 备份（39 万行） | 0.2 s，1.4 MB |
| 恢复（39 万行） | 秒级，数据一致 |

Windows 实机因文件系统与杀毒软件差异，导入吞吐可能低 20–40%；如需基线，请在目标机重跑：

```powershell
python tools\perf_bench.py --api http://127.0.0.1:8000 --admin <账号> --admin-password '<口令>' --latency --throughput --import 20000 --soak 60
```

## 八、故障处理

| 症状 | 排查顺序 |
|---|---|
| 双击无反应 / 白屏 | ① `Logs\` 最新日志 ② `aims_crash.log` ③ `deploy status`（数据库是否 running）④ 端口 8000 是否被占用 |
| 启动报"数据库程序已就位，但数据目录不存在" | 数据目录被移动或 `AIMS_DATA_ROOT`/`AIMS_PG_DATA` 指向别处。**不要**用空库继续跑；确认原数据目录后修正环境变量或恢复数据 |
| 安装最后一步报健康检查失败 | 看 `Logs\post-install-doctor.json` 的 `→` 建议；常见为端口冲突、磁盘不足、服务注册失败 |
| 数据库起不来 | `Logs\` 下 PostgreSQL 日志；`pg_ctl status`；磁盘是否满；`postmaster.pid` 是否残留 |
| 登录提示"登录已失效" | 1.0.0 会明确提示重新登录（System → Login）。若频繁出现，检查服务器时间是否漂移（JWT 依赖系统时钟） |
| 频繁 429 | 触发限流：认证 20 次/分钟、业务 600 次/分钟；或账号被锁定（5 次/15 分钟）。等待或换账号 |
| 导入报 409 | 数据与已有记录冲突（历史库缺少联合主键导致无法幂等写入），本次导入已整体回滚，数据库未改动 |
| AI 回答很慢 | 未装 llama.cpp 时走规则引擎（快）；本地模型推理受 CPU/内存限制，检查是否加载了过大模型 |

### 收集诊断包

开始菜单「AIMS 诊断报告」→ 生成 `diagnose` 输出；或：

```powershell
& $BE deploy --root $APP doctor --api-port 8000 --json "$env:TEMP\doctor.json"
```

把 `doctor.json` + `Logs\` 最近 3 个日志 + `aims_crash.log` 一起提交给技术支持。**提交前检查日志中是否含口令/密钥**。

## 九、CLI 速查

```powershell
& $BE deploy --root $APP provision      # 初始化/修复部署（安装程序调用）
& $BE deploy --root $APP upgrade        # 只升级结构，保留数据与配置
& $BE deploy --root $APP doctor         # 健康检查
& $BE deploy --root $APP status         # 部署状态
& $BE deploy --root $APP start|stop     # 启停数据库
& $BE deploy --root $APP backup --reason manual
& $BE deploy --root $APP backups        # 备份列表
& $BE deploy --root $APP restore latest --yes
& $BE deploy --root $APP selftest       # 真实业务自检（34 项）
& $BE deploy --root $APP ai-probe       # AI 引擎自检
& $BE deploy --root $APP uninstall [--purge --yes]
& $BE deploy --root $APP version
```

`uninstall` 默认**保留**数据；`--purge` 需同时 `--yes`，且会先做一次安全备份。

## 十、安全运维检查清单（建议每季度）

- [ ] 修改所有默认/共享账号口令，禁用离职人员账号
- [ ] 确认 `APP_ENV=production`（关闭 `/docs`、`/openapi.json`）
- [ ] 跑一次 `tools\security_audit.py`，确认高危 0
- [ ] 跑一次 `pip-audit -r requirements-exe.lock --disable-pip --no-deps`，有漏洞则升级并回归
- [ ] 验证备份可恢复（在测试机）
- [ ] 检查 `Logs\` 是否有异常登录、频繁 429、越权 403
- [ ] 检查磁盘剩余与数据保留策略是否符合合规要求
- [ ] 确认安装包与发布清单哈希一致
